## Goal

The database schema for v1.0 exists:
- written down in `docs/db-schema.md`, the missing document from 00 §2;
- built as SQLAlchemy models and an Alembic migration;
- every tenant table isolated by RLS, and tests that prove it.

## Tasks

### Backend
- [x] `docs/db-schema.md`: 50 tables (39 tenant under RLS, 11 global) with columns, types, keys, indexes, layer and RLS policy. **Signed off by the user before the migration.**
  - Table names differ from the draft list above: `catalog_items` (not `master_catalog_items`), `knowledge_candidates` (not `shared_knowledge_queue`, and a tenant table), `products` (not `price_list_products`).
  - Added beyond the draft: the global `reference_crops`, `abbreviations`, `vat_rates` and `fx_rates`; the tenant `panels`, `context_artifacts`, `stage_runs`, `components`, `suppliers`, `brand_discounts`, `derived_item_rules`, `tenant_abbreviations`, `tenant_reference_crops`, `tenant_rule_overrides`, chat tables, and audits.
- [x] SQLAlchemy 2 models in `konboro/db/models/`:
  - `global_`, `account`, `pipeline`, `quotes`, `pricing`, `learning`.
  - Shared types and helpers live in `konboro/db/base.py`: `Money`, `Rate`, `Qty`, `one_of()` (CHECK enums), `tenant_fk()` (composite foreign keys).
- [x] `konboro/db/ids.py`: prefix + ULID, no dependency.
- [x] Alembic `0001_initial_schema`:
  - Autogenerated tables, plus the pgvector extension.
  - RLS `ENABLE` + `FORCE` + policy `tenant_isolation` on 39 tables.
  - Grants: `SELECT` only on global tables; DML on tenant tables.
  - Triggers: sent versions and their lines are immutable; correction events are append-only.
- [x] Two roles:
  - `konboro` owns the tables and runs migrations.
  - `konboro_app` is the app role. It is not a superuser, has no `BYPASSRLS` and owns nothing. `konboro/db/bootstrap.py` creates it, with a password from the environment.
- [x] `konboro/db/session.py`:
  - `tenant_session(tenant_id)` validates the id, then runs `set_config('app.tenant_id', …, true)` (SET LOCAL semantics).
  - `global_session()` sees no tenant rows.
- [x] `make migrate` and `make seed`.
  - The seed creates the demo tenant "לוחות דמו בע\"מ": owner user, settings, default 25% markup rule, all 5 v1.0 flags on, quota 12 of 50.
  - It adds a made-up customer and project, 5 suppliers, and the prototype's 23 products plus one consumable.
  - It also seeds the global plans, flags and VAT 18%.

### Integration tests (230 new)
- [x] The migration applies cleanly up, down and up again (`test_migration_downgrades_and_upgrades_cleanly`).
- [x] **Cross-tenant suite**, parameterized over all 38 tenant tables. Tenant B cannot read, update, delete or insert A's rows, and cannot move its own row to A.
  - Every table has data from `factory.py`, which builds one row in every tenant table through the app role.
- [x] Guards that catch future gaps:
  - Every table with `tenant_id` (and `tenants`) has forced RLS and the policy (reads `pg_class` / `pg_policies`).
  - The factory covers every tenant table.
  - `konboro_app` is not a superuser, has no BYPASSRLS, and owns no table.
- [x] Without tenant context, nothing is visible in any tenant table and nothing can be written. Invalid tenant ids, including SQL-injection-shaped ones, are rejected before reaching the DB.
- [x] Global tables are readable and not writable by the app.
- [x] Database rules:
  - `Decimal('1250.10')` round-trips exactly.
  - No money, rate or price column is float.
  - A sent version and its lines cannot change; a draft can.
  - Correction events allow only `undone` to change, and no deletes.
  - At most one preferred supplier per product.
  - Margin must be below 100%.
  - A composite foreign key rejects pointing at another tenant's drawing.
- [x] Seed: two runs give the same result. Prices are exact. The demo data is visible to the app inside the demo tenant only.
- [x] **Mutation check of the suite itself.** With RLS removed from `customers` in the migration, all 5 `customers` tests and the guard failed. Restored afterwards.
  - This found one weak test: "move own row" passed even without RLS, because a foreign key also blocked the move. It now requires the RLS error.

## Outcome

- **Done:**
  - The full v1.0 schema (50 tables) in one migration, with four layers of tenant isolation.
  - The demo seed.
  - 263 backend tests, 230 of them new integration tests.
- **Decisions made:**
  - From the user, at kickoff:
    - Build the whole v1.0 schema now, in one migration: tenant layer, global layer, price list, margin rules and approval queue. Later sessions only add columns.
    - The demo seed uses made-up names: factory "לוחות דמו בע\"מ" and a made-up customer. The technical drawing content is real (NURSERY-1). Real customer names never go into demo environments.
  - Settled by the specs (no question needed):
    - IDs are a prefix plus a ULID. The spec examples (`drw_01J…`) are ULIDs.
    - Quote lines are soft-deleted (`deleted_at`). Every deletion is a `row_deleted` correction event that undo must be able to reverse (09 §10).
  - Approved by the user with the schema document:
    - **Quantity is `numeric(12,3)`, not int.** Products sold by the meter (07 §7.2.1). Spec 07 §6.2 is updated.
    - **Composite foreign keys** `(tenant_id, id)` on every tenant relation.
    - Triggers make sent versions immutable and correction events append-only.
    - Approval-queue promotion runs as the owner role, never the app.
  - Made while implementing:
    - **The app role is created by a bootstrap script, not the migration.** It needs a password, and roles are cluster-wide. The migration creates it as `NOLOGIN` if bootstrap hasn't run, so grants never fail.
    - **`quota_usage` has a `counter` column** (`quote` / `audit`) in its key. A plan with a separate `monthly_audit_limit` needs two counters per month (01 §4.3).
    - **The migration lists its tables statically**, so it doesn't change when the models change later.
    - On `correction_events`, the append-only trigger fires before RLS. The "move own row" test accepts either refusal for that table; RLS on it is proven by the other tests.
- **Bugs logged:** none.
- **Follow-ups:**
  - S03 uses `tenant_session` for every request and puts `konboro_app` behind the API.
  - S29 creates `konboro_app` in Terraform, with its password in Secrets Manager.
